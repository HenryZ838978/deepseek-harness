# DeepSeek V4-Pro / V4-Flash 边界探测报告 — 2026-05-09

**Endpoint**: `https://api.deepseek.com` (官方)
**Models**: `deepseek-v4-pro`, `deepseek-v4-flash`
**Total trials**: 270+ across 11 probe types × 2 models
**Total findings**: 14 distinct
**Cost**: ~$2.5

> **Methodology**: 所有 probe 严格 mirror DeepSeek 官方文档示例 (multi_round_chat, function_calling)
> — 不使用任何我们自己的 salvage 库，纯 `from openai import OpenAI`。这样测出来的 bug
> 能直接归因到「DeepSeek + 标准 SDK」组合，而非我们的封装。

---

## TL;DR — 你必须立刻知道的 7 件事

1. **`deepseek-v4-pro/flash` DEFAULTS to `thinking=enabled`** — 每次调用至少烧 ~30 reasoning tokens。Agent 框架若没有显式 `extra_body={"thinking":{"type":"disabled"}}`，token 账单会比预期高 2-5 倍。
2. **reasoning_content lifecycle bug 100% 复现且未修** — 多轮工具循环不回传 `reasoning_content` → `400 The reasoning_content in the thinking mode must be passed back to the API`。**V4-Pro 与 V4-Flash 都中招**。
3. **平行 tool_calls 的 streaming chunk 是 INTERLEAVED 的** — 任何按 list-index 顺序累积的 client 会炸（必须用 `dict[int]` 按 `tc.index` 累积）。
4. **真实上下文上限 = 1,048,576 tokens (1M)** — 文档没明说，超过就 `400 This model's maximum context length is 1048576 tokens`。
5. **缓存命中规则比文档更宽松**：中段扰动后**前 512 tokens 仍能命中**(38%)，并不是"一字节差全失效"。但末端扰动 100% 保留 head cache。
6. **streaming chunk 极细粒度 (1-3 chars / chunk)** — V4-Pro 一次普通对话能产生 **1700+ chunks**，自我怀疑型 prompt 能产生 **8000+ chunks**。任何 `state += chunk` 写法的客户端面临 O(n²) 内存压力 → ChatWise 那种 `Invalid string length` (V8 512MB 上限) 就来源于此。
7. **V4-Flash ≠ "修过的便宜版"**：bug 清单 1:1 对应 V4-Pro，**仅 latency 和 cost 不同，protocol 契约完全一致**。任何针对 V4-Pro 的适配都需要在 V4-Flash 上一字不改地工作。

## 详细数据

### 1. Streaming chunk shape (probe_1, n=3)

```
chunk-shape distribution across 61 chunks:
  content:           55  ← 普通文本 delta
  empty:              3  ← 完全空 chunk (cline #1594 trigger)
  finish=stop+usage:  3  ← 终结 chunk，仅含 usage
```

**Spec rule**: client 必须 tolerate `chunk.choices == [] and chunk.delta is None`。

### 2. reasoning_content lifecycle (probe_2, n=3 trials × 3 phases)

| phase | 期望 | 实际 |
|---|---|---|
| setup (生成 tool_call + reasoning_content) | 200 | 3/3 OK |
| A_faithful (回传 reasoning_content) | 200 | 3/3 OK |
| B_stripped (丢掉 reasoning_content) | 400 | **3/3 BadRequestError** |

**400 message 一字不差**:
> `The reasoning_content in the thinking mode must be passed back to the API.`

→ Spec §1 直接引用此原文。

### 3. tool_call leakage (probe_3 thinking OFF, n=30 + probe_3b thinking ON, n=20)

总 50 次：
- content-field 漏水: **0**
- reasoning_content 漏水: **0**
- 全部 `finish_reason="tool_calls"`，`tool_calls` 字段正确填充

→ DeepSeek-V3#1244 在 V4-Pro 上**已修复**。Spec §2 的 salvage 仍有价值（防御 vLLM/SGLang/OpenRouter 等第三方 endpoint），但官方 endpoint 不需要。

### 5. Cache prefix sensitivity (probe_5)

System+user prefix ≈ 1336 server tokens。

```
S1 identical prefix:
  S1#0:    0% (cold start)
  S1#1: 95.8% (1280/1336)
  S1#2: 95.8%
  S1#3:  0%   ← cache eviction in the wild!
  S1#4: 95.8%
  S1#5: 95.8%
  S1#6: 95.8%
  S1#7: 95.8%

S2 middle-char flip per call:
  S2#0:  0% (cold)
  S2#1: 38.3% (512/1336)  ← 重大发现：中段扰动后前 512 tokens 仍命中
  S2#2-S2#6: 38.3%
  S2#7: 95.8%               ← 偶尔扰动落在 token 边界外，整个 prefix 仍 hit

S3 last-char flip:
  S3#0-S3#7: 95.8% (all)    ← 末端扰动完全保留 head cache
```

**Spec rule update for §4**:
- 最小缓存粒度看起来是 **256 tokens**（1280 = 5 × 256，512 = 2 × 256）
- 中段扰动**不是全杀**——前 N 个 256-token blocks 仍命中
- cache eviction 事件存在（S1#3）— agent 不能假设 cache hit 永远稳定

**Cache field double-naming 实证** (every probe usage block):
```python
{
  "prompt_tokens": 1336,
  "prompt_cache_hit_tokens": 1280,             # DeepSeek native
  "prompt_cache_miss_tokens": 56,
  "prompt_tokens_details": {"cached_tokens": 1280},  # OpenAI shape
}
```
两个字段同时存在 — vanilla OpenAI parser 仍会读到正确值。**好消息**：这个 bridging 在 v4 上是冗余的（两个字段都填了），但不同 SDK 版本可能只读一个，所以 `normalize_usage()` 仍然必要。

### 6. Context window (probe_6 + probe_6b)

| target | server_tokens | cold latency | warm latency |
|---|---|---|---|
| 16K   | 10,093    | 2278 ms | 738 ms |
| 64K   | 39,110    | 1591 ms | 1473 ms |
| 128K  | 79,441    | 1841 ms | 1335 ms |
| 200K  | 197,912   | 5064 ms | (not measured) |
| 500K  | 494,559   | 8085 ms | (not measured) |
| 800K  | 792,075   | 12474 ms | (not measured) |
| 1M    | 989,913   | **15566 ms** | (not measured) |
| **1.06M+** | rejected | — | — |

**Hard ceiling**: 1,048,576 tokens (= 2^20 = 1 MiB tokens)

**Reject error message**:
> `This model's maximum context length is 1048576 tokens. However, you requested 1060836 tokens (1060828 in the messages, 8 in the completion). Please reduce the ...`

**Latency curve**: 大约 **1.5 ms / 1K input tokens** linear scaling 到 1M。

**Tokenizer 压缩比**：DeepSeek v4 tokenizer 对重复英文 ASCII 大约 **3.6 chars/token**（比 cl100k_base 的 ~4 chars/token 略密；对完全随机字母约 3 chars/token）。

### 7. Parallel tool streaming (probe_7, n=3)

```
trial 0: chunks=30 indexes=[0, 1] interleave=True
trial 1: chunks=30 indexes=[0, 1] interleave=True
trial 2: chunks=30 indexes=[0, 1] interleave=True
```

3/3 都 interleave。Function name 100% 在该 index 的第一个 chunk 出现。Arguments 拼出来：
- index 0: `{"expression": "(12 + 34) * 56"}`
- index 1: `{"query": "TCP slow start"}`

**Spec rule**: client MUST aggregate by `dict[tc.index]`, NOT `list.append`.

### 8. finish_reason semantics (probe_8, n=3 × 3 cuts)

| cut | finish_reason | content_len | tool_calls |
|---|---|---|---|
| C1 length (max_tokens=8 + tool定义) | `length` | 0 | 0 |
| C2 normal stop | `stop` | 21 | 0 |
| C3 refused word | `stop` | 7 | 0 |

**Finding #5**: thinking-OFF + max_tokens=8 + 有 tool 定义 → 模型连 tool_call 都没开始就被切了。`length` 出现时 content/tool_calls 都可能是空。Agent 不能假设 length cut 一定有部分内容。

## 新增 probe 详细数据（针对 ChatWise 截图 + 用户多轮抱怨）

### probe_9 reasoning_content runaway (V4-Pro)

| prompt | reasoning_bytes | content_bytes | n_chunks | finish | bailed |
|---|---|---|---|---|---|
| T1 paradox | 2,954 | 4,788 | 1,713 | stop | no |
| T2 long_chain | 1,422 | 2,253 | 1,305 | stop | no |
| T3 self_doubt | **26,196** | 3,715 | **7,941** | stop | no |

**关键观察**: V4-Pro 的 reasoning **是有界的**（最难 prompt 也只到 26 KB / 84 秒），所以 ChatWise 的 512MB 不是单次响应导致的，而是：

1. 流式 chunk 极细 (1-3 chars per chunk on reasoning) — V4-Pro 一次响应 1700-8000 chunks
2. 客户端 naive `state.content += chunk` 字符串拼接 → **O(n²) 内存压力**
3. 历史多轮累积 + 没设 `max_tokens` 上限 → 总 buffer 触顶

V4-Pro 自身没有失控，**问题在客户端**。建议任何 OpenAI 兼容客户端处理 DeepSeek 流时使用 list buffer + 末尾 `"".join(buf)`，或者直接 `array.array("u")` 拼接。

### probe_10 multi-turn agentic loop (V4-Pro & V4-Flash 全过)

5 轮 multi-round chat (S1) + 5 轮 single-tool loop (S2) + 5 轮 multi-tool + thinking (S3)

| 模型 | scenario | 0 errors | reasoning 400s | tool leaks | 5-turn 累计 history |
|---|---|---|---|---|---|
| V4-Pro | S1 chat | 5/5 | n/a | n/a | 4,102 bytes |
| V4-Pro | S2 single-tool | 5/5 | n/a | 0 | 2,991 bytes |
| V4-Pro | S3 multi-tool + thinking | 5/5 | **0** | 0 | 4,106 bytes |
| V4-Flash | S1 chat | 5/5 | n/a | n/a | 3,459 bytes |
| V4-Flash | S2 single-tool | 5/5 | n/a | 0 | 3,431 bytes |
| V4-Flash | S3 multi-tool + thinking | 5/5 | **0** | 0 | 3,926 bytes |

**S1 cache hit 累积曲线 (V4-Pro)** — 教科书级案例：

```
turn 0: 0/13      (cold start, prefix < 1024)
turn 1: 128/227   (56% hit)
turn 2: 256/354   (72% hit)
turn 3: 384/494   (78% hit)
turn 4: 640/675   (95% hit)  ← 多轮缓存自然增长
```

**V4-Flash 同场景 cache 命中曲线**：稍逊 (turn 3 突回 0)，可能是 Flash 模型 cache buckets 更小或 eviction 更快。

→ **结论**：只要 client 「正确保留 reasoning_content + 正确路由 tool messages」就完全无 bug。社区的多轮抱怨大概率来源于 client 错误丢字段，不是模型本身。

### probe_11 V4-Flash 全量扫 (vs V4-Pro 同 probe)

V4-Flash 在所有 8 个 probe 上的行为与 V4-Pro **1:1 对应**：

- probe_2: 3/3 reasoning-strip 400 复现 ✓
- probe_3: 0/30 leakage ✓
- probe_3b: 0/20 leakage (thinking ON) ✓
- probe_5: cache 曲线完全一致 (1280/1336 = 95.8% warm) ✓
- probe_7: parallel tool **interleave 38 chunks** (Pro=30, Flash 更细粒度) ✓
- probe_10: 15/15 turns 全 OK ✓

**唯一差异**：latency 与 cost。Flash 平均 ~2-5s/turn，Pro 4-9s/turn，差 ~2x。

→ **任何 V4-Pro 适配可一字不改地复用到 V4-Flash**。这是好事——开发者只需要适配一次。
