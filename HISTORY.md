## 2026-08-21 · `@deepseek-ai/dsh` **0.1.1-rc.2** (35 commits since rc.1, ~6 hours later; **promoted to `latest`** — first version made general-audience since 0.1.0-rc.7)

Nearly the whole diff is one topic: unified request-image pipeline with the new DeepSeek Files API upload path. `feat(images): unify master and Files request pipeline` + `fix(llm-deepseek): fall back when Files resolution fails` + `fix(deepseek): decouple files and stream timeouts`.

- **All 8 previous defects still present** at tag `dsh-v0.1.1-rc.2`. Same grep as rc.1: `spillAll` / `stripBOM` / `api-request-trust host===` / `session-persistence flock` / `SENSITIVE_ENV_PATTERN` / `subagent-codex readFileSync` / `adapter.ts hasImages throw-after-append` all byte-identical.
- **New: DeepSeek Files API upload-index is not cross-instance safe under one API key.** `packages/llm/llm-deepseek/src/file-store.ts:reclaimOldestOwned` deletes remote /files entries whose filename starts with `OWNED_FILE_PREFIX = 'dsh-'`. The prefix is dsh-ecosystem-wide, not per-install. Two dsh installs sharing one API key (team, CI, one dev + two machines) each maintain a separate local `~/.dsh/llm-deepseek/files-v3.json` but hit the same remote quota — when A's `reclaimOldestOwned` fires, it happily deletes file_ids B is still using. DSH-side, not a wire bug; users who wonder "why can't the model see the fine text in my screenshot" are looking at this. sharp/libvips is well-behaved code — the concern is the policy, not the implementation.
- **Observed but not a probe: no slice/tiling on dsh side.** grep for `slice|tile|patch` on the image pipeline returns 0 matches unrelated to hash prefixes. DSH sends one flat image (via data URL or file_id); server-side tiling is the model's problem, not dsh's. Architectural choice, not a defect — recorded so the map is complete.
- **Observed but not a probe: no vision streaming prefill.** Vision content is fully assembled before `stream()` opens. Aligns with DeepSeek chat/completions capabilities; no gap here.

## 2026-08-27 · `@deepseek-ai/dsh` **0.1.2-alpha.1** (1079 commits since rc.2; GitHub tag + release only — **not published to npm**)

npm `@deepseek-ai/dsh` `latest` and `next` both still resolve to `0.1.1-rc.2` at the time of this audit. rc.8 was "`next`, not yet `latest`"; this one is neither. The release notes list 100+ user-visible changes and read as a product release; `npm i @deepseek-ai/dsh@0.1.2-alpha.1` does not resolve. Audited from the source tag (`cd5ef81`).

- **FIXED — P3-serve (#2573), the first defect this doctor covered that upstream has eliminated.** `client/connection/src/api-request-trust.ts` no longer does the literal `host ===` compare. Host authorities are normalized through WHATWG (`parseAuthority`), matched against a configured `trustedHosts` allowlist (`isTrustedAuthority`; port-less entries match any port, `:80`/`:443` still judged explicit via dual-scheme parse), an explicit `sec-fetch-site: cross-site` is refused, and the Origin fence is retained. `assertTrustedAuthority` rejects non-canonical config spellings (`0x7f.0.0.1`, percent-encoding, unbracketed IPv6, zero-padded ports, `host/path`, `user@host`) at load. **No acknowledgement or reference to our Discussion #2573.** → `dsh doctor --node --only P3-serve` now reports which fence generation a server runs.
- **New (not a defect): browser-session authentication.** `client/connection/src/browser-auth.ts` (313 lines, new file) — one-time process launch token at `/?token=`, exchanged for an HMAC-SHA256 signed cookie then 303-redirected to a clean `/`. `timingSafeEqual` compares, base64url round-trip validation rejecting variant encodings, authority-bound payload, HttpOnly + SameSite=Strict, absolute expiry bounded by `cookieMaxAgeDays`. `rpc-host.ts:requestRejection` is now two fences: 403 on Host/Origin failure, 401 on missing/invalid cookie. Audited and found sound; recorded because it changes P3's expected wire behaviour (unauthenticated loopback data calls now answer 401, not 101/200/404).
- **Still present, per grep at tag `cd5ef81`:** P2-bom (`stripBOM` — 0 occurrences repo-wide; `boot/app-boot/src/profile.ts` has 5 bare `JSON.parse(readFileSync(...))` sites, package moved `packages/app/` → `packages/boot/`) · P4-spill (`subprocess-local/src/spawn.ts:156` `spillAll` — `openSync`/`writeSync` still unguarded; the function did gain `'wx'` + `0o600` + random suffix, which is symlink-planting hardening, not error handling; sibling `discardSpill` still has both try/catch) · P5-seqgap (`packages/session/` — `flock|O_EXCL|lockf|withFileLock` = **0 occurrences**, while `credentials-local/src/index.ts:684` uses `withFileLock`) · P6-subagent-env-scrub (`subprocess/src/index.ts:44` byte-identical) · P7-subagent-codex-preflight (`subagent-codex/src/run.ts:43-45` top-level `resolve` + `readFileSync` + `JSON.parse`, no try/catch) · P8-multimodal-preflight (`llm-deepseek/src/adapter.ts:457-467` throws `UNSUPPORTED_CONTENT` inside `stream()`; `agent-loop/src/agent.ts:290` appends `user/message` before `:362` calls `stream()` — the half-turn commit path is intact, only the line numbers moved) · P9-files-quota-scope (`file-store.ts:12` `OWNED_FILE_PREFIX = 'dsh-'`, `:304` `reclaimOldestOwned` filter byte-identical). **7 of 8 still present.**
- **New: jsonl session repair truncates without the staleness check its sqlite sibling has.** The release ships "warn when automatically repairing a truncated conversation-log tail" — the warning is real (`session-persistence-jsonl/src/index.ts:459`), the guard is not. Same `commitRepair` interface, two implementations: sqlite (`session-persistence-sqlite/src/store.ts:214-236`) opens `begin-immediate`, re-scans, and throws `repair is stale: physical tail no longer starts at seq N` if the tail moved — or `repair omitted current torn tail` if one appeared; jsonl (`index.ts:451-459`) calls `repair()` unconditionally, which is a bare `truncate(path, offset)` + fsync, then warns after the fact. A second process appending at the truncation offset in that window loses its committed event silently. jsonl is the default backend (`bundle/base/package.json` depends on it); sqlite — the one with the check — is opt-in. → **`dsh doctor --node --only P10-jsonl-repair-unguarded`**
- **Observed, not a defect: WebFetch public-network default.** `web/web-fetch-http/src/network.ts` pins the resolved address for the connection "so the connection cannot resolve the hostname again to a private address" — DNS-rebinding defence done the correct way. Enabling public WebFetch without per-request approval is a policy change, and the SSRF control backing it is sound.
- **Third consecutive release to disclose a boundary limitation and ship anyway.** `SAFETY.md` now states DeepSeek Harness "has not been security-audited, and sandboxing, approvals, and permissions do not guarantee isolation." Follows rc.8's agent-team README ("not cross-process exactly-once delivery") and rc.1's credentials-local README ("that is discretion, not a boundary"). The pattern is consistent and, to be fair, honest.

## 2026-09-01 · `@deepseek-ai/dsh` **0.1.2-alpha.4** (tag `4e84901e`; `alpha` tag moved here, skipping past alpha.3 `dd6322d6` of 08-31)

Dist-tags at audit time: `{"latest":"0.1.1-rc.2","next":"0.1.1-rc.2","alpha":"0.1.2-alpha.4"}`. `latest` and `next` have now sat on 0.1.1-rc.2 through **four** 0.1.2 releases. alpha.3 shipped to npm but was never pointed at by a tag, so it is audited here as the release that carried the change, and alpha.4 as the one users actually resolve. Upstream tags are `dsh-v0.1.2-alpha.N`, not `v0.1.2-alpha.N` — the latter 404s.

- **P10's control group was deleted. The defect was not.** alpha.3 removed the SQLite session backend outright. `.agents/notes/implemented/simplification/2026-08-30-jsonl-only-session-persistence.md` states it directly: `@deepseek-ai/dsh-session-persistence-jsonl` "is the sole first-party implementation of `ctx.sessionPersistence`", and the sqlite "package, its schema resources, backend-specific tests, configuration surface, and Windows differential lane are absent." On alpha.4, `grep -rn "async commitRepair" --include="*.ts" packages/ | grep -v tests` returns exactly **one** production hit — `session-persistence-jsonl/src/index.ts:469`, still 6 lines, still 0 staleness checks. `packages/session/` has no `*sqlite*` directory; the surviving `packages/storage/storage-sqlite` (domain-KV) and `packages/session-query/session-query-sqlite` (disposable FTS index) contain **zero** occurrences of `commitRepair`. npm confirms the stop: `@deepseek-ai/dsh-session-persistence-sqlite` still has `alpha` → `0.1.2-alpha.2`. The 25-line guarded implementation — `begin-immediate`, re-scan, three staleness throws — is now absent from the tree entirely. The removal is defensible on its own terms and the note is candid that it "removes the stronger database/WAL storage option"; the consequence for P10 is simply that the careless implementation is no longer the *default* one of two, it is the *only* one. → **`dsh doctor --node --only P10-jsonl-repair-unguarded`**
- **P4 hardened against a different threat; the reported defect is untouched.** `subprocess-local/src/spawn.ts:169` now opens the spill file as `openSync(this.spillFile, 'wx', 0o600)`, with a `randomBytes(6)` suffix built at `:167`, commented "defeats spill-path prediction and symlink planting in shared tmp dirs." That is path security, not error handling. `spillAll` (`:156-174`) still contains **zero** `try`, while `discardSpill` directly below it contains **three** — the asymmetry that was P4's original tell is unchanged. `'wx'` (O_EXCL) gives `openSync` one *more* way to throw, and `push()` at `:134` still calls `spillAll(chunk)` bare inside a stream `'data'` callback. Recorded explicitly so a future pass does not misfile this as a fix. → **`dsh doctor --node --only P4-spill-dir`**
- **P9 still un-scoped; the new method name invites a false read.** `file-store.ts:12` is still `const OWNED_FILE_PREFIX = 'dsh-'` — a fixed string with no host, install, or user component — and `reclaimOldestOwned` (`:288-313`) still selects purely on `file.filename.startsWith(OWNED_FILE_PREFIX)` before deleting. "Owned" means owned by dsh the product, not by this installation of it, which is the defect rather than its remedy. P6 byte-identical (`subprocess/src/index.ts:44`). P2, P5, P7, P8 unchanged. **P3 remains fixed; not regressed.**
- **Audited, not a defect: `web_fetch` now on by default in `dsh-base`.** `packages/bundle/base/cordis.patch.yml:462-465` mounts `dsh-tool-web` with `fetch: true`, so headless, SDK, ACP, and every base-backed profile inherit anonymous public fetch with no per-call approval. The SSRF surface holds up under reading: `web-fetch-http/src/network.ts` resolves the hostname once, rejects the **entire** answer set unless every address is public unicast, classifies IPv4-mapped IPv6 by its embedded address, discovers NAT64 prefixes via RFC 7050 and re-checks the translated IPv4, then pins those addresses into Undici through a custom `lookup` so the connection cannot re-resolve — DNS-rebinding closed. Redirects are `manual`: `provider.ts:65-113` re-runs `validateFetchUrl` **and** full address re-resolution on every hop, and refuses cross-origin redirects outright. It uses `ipaddr.js`, not the `ip-address` package that produced CVE-2026-69192. Upstream's own line — "public-destination validation does not prevent public data egress" — is an accurate capability statement, not an unguarded hole.
- **Audited, not a defect: branded `SessionSeq` / `SessionLogOffset`.** `.agents/notes/implemented/architecture/2026-08-31-session-sequence-and-log-offset-brands.md` splits event identities from log offsets at the type level and drops `seedLength` from the logical header in favour of `isSeeded`. The v0 JSONL header stays byte-compatible (absent → `isSeeded: false` cut 0; present zero or nonzero → `isSeeded: true` with the exact cut) and the note states plainly that a compile-time brand "does not discover unknown numeric fields in an external event". Checked because it touches the same seq field as P5; it is a compile-time change and does not affect the cross-process race.
- **Probe changes: three docstrings, no logic.** P10 lost the sibling comparison in its title, detail text, and `upstream_ref` evidence (now recording `production_commitrepair_impls: 1` and citing the removal note); P4 and P9 gained alpha.4 re-verification paragraphs warning against the two false-fix readings above. Detection logic is untouched — 27 tests pass, `ruff` count unchanged at 8 pre-existing.

## How to read this file

- **All entries are code-referenceable.** Every claim above cites a specific file or a specific defect id from the official `deepseek-ai/deepseek-harness` GitHub Discussions.
- **The fix column is always `dsh doctor --node`.** That command is: `pip install deepseek-harness-cli && dsh doctor --node`. It runs nine probes offline and one live-network probe (P3-serve); each reports what the official Node stack does not.
- **Cross-check.** Every probe's source is [packages/cli/deepseek_harness_cli/doctor_node/](packages/cli/deepseek_harness_cli/doctor_node/) in this repo. Every "still present" claim is a `grep` you can run against the compiled rc.N artifact from `npm view @deepseek-ai/dsh@<version>`.
